모든 취약점이 항상 0개라는 보장이 아니라, 취약점 유형에 맞는 업데이트 경로를 조합해 패치 지연과 다운타임을 줄이는 운영 모델을 의미합니다.

실습용 Source Image

quay.io/yeslee/rhel10-bootc:10.2에는 kpatch 실습에 사용할 kernel-6.12.0-211.16.1.el10_2가 사전에 고정되어 있고, 기본 실습에 필요한 패키지를 제공하는 workshop-rhel10 DNF Repository 설정도 포함되어 있습니다. 따라서 Step 1~6에서는 참가자가 RHSM을 별도로 등록할 필요가 없습니다. 참가자는 해당 base image를 기반으로 Hardening과 Image Mode 업데이트 흐름에 집중합니다.

2-2. Hardened Containerfile

Containerfile · :hardened 전체
bootc container lint컨테이너가 bootc OS 이미지로 사용할 수 있는 기본 구조를 충족하는지 검사합니다.
cat <<'EOF' > Containerfile.hardened
FROM quay.io/yeslee/rhel10-bootc:10.2

ARG LAB_PASSWORD_HASH

# ------------------------------------------------------------
# 0. 실습용 Source Image의 kernel 검증
#    Source Image 자체에 kpatch 실습 대상 kernel이 사전 고정되어 있습니다.
# ------------------------------------------------------------
RUN rpm -q kernel-core     | grep -q '6.12.0-211.16.1.el10_2'

# ------------------------------------------------------------
# 1. 실습 및 검증에 필요한 패키지 설치
# ------------------------------------------------------------
RUN dnf install -y \
    openssh-server \
    sudo \
    podman \
    rhc \
    insights-client \
    kpatch \
    kpatch-dnf \
    && dnf clean all

# ------------------------------------------------------------
# 2. 재부팅 후 접속할 lab-user 구성
# ------------------------------------------------------------
RUN if ! id lab-user >/dev/null 2>&1; then \
        useradd -m -s /bin/bash lab-user; \
    fi \
    && usermod -aG wheel lab-user \
    && usermod -p "${LAB_PASSWORD_HASH}" lab-user \
    && mkdir -p /etc/sudoers.d \
    && printf '%s\n' \
       'lab-user ALL=(ALL) NOPASSWD: ALL' \
       > /etc/sudoers.d/lab-user \
    && chmod 440 /etc/sudoers.d/lab-user

# ------------------------------------------------------------
# 3. SSH 비밀번호 로그인 허용 - 실습 편의용
# ------------------------------------------------------------
RUN mkdir -p /etc/ssh/sshd_config.d \
    && printf '%s\n' \
       'PasswordAuthentication yes' \
       'KbdInteractiveAuthentication yes' \
       'PermitRootLogin no' \
       > /etc/ssh/sshd_config.d/00-lab-access.conf \
    && systemctl enable sshd.service

# ------------------------------------------------------------
# 4. SELinux Enforcing 유지
# ------------------------------------------------------------
RUN sed -ri \
    's/^SELINUX=.*/SELINUX=enforcing/' \
    /etc/selinux/config

# ------------------------------------------------------------
# 5. 기본 hardening sysctl
# ------------------------------------------------------------
RUN printf '%s\n' \
    'net.ipv4.conf.all.rp_filter=1' \
    'net.ipv4.tcp_syncookies=1' \
    'kernel.unprivileged_bpf_disabled=1' \
    > /etc/sysctl.d/99-hardening.conf

# ------------------------------------------------------------
# 6. 실습 단계 식별용 marker
# ------------------------------------------------------------
RUN printf '%s\n' 'hardened' \
      > /usr/share/lab-image-stage \
    && printf '%s\n' '1.0' \
      > /usr/share/lab-userspace-generation

# bootc image에 kernel이 정확히 1개만 포함되어 있는지 포함해 최종 구조 검증
RUN bootc container lint
EOF

3-3. SSH host key 갱신 후 재접속 — Windows / macOS / Linux

system-reinstall-bootc로 root OS를 교체하면 새 RHEL 10.2 이미지에서 SSH host key가 새로 생성될 수 있습니다. 기존에 같은 hostname으로 접속한 적이 있는 PC는 이전 key와 새 key가 다르기 때문에 REMOTE HOST IDENTIFICATION HAS CHANGED! 경고를 표시하고 연결을 차단할 수 있습니다.

운영체제와 관계없이 핵심은 동일합니다.

OpenSSH의 ssh-keygen -R <hostname> 명령으로 해당 호스트의 이전 key만 known_hosts에서 제거한 뒤 다시 SSH로 접속합니다. Windows PowerShell, macOS Terminal, Linux shell에서 같은 방식으로 사용할 수 있습니다.

5-4. soft reboot 전 Kernel 버전 확인

다음 단계에서는 Kernel은 그대로 유지한 채 Userspace만 새 이미지로 변경하는 soft reboot를 수행합니다. 따라서 먼저 :hardened 이미지와 새로 만든 :userspace-update 이미지에 포함된 Kernel 버전이 서로 같은지 확인해야 합니다.

왜 확인하나요?

soft reboot는 현재 실행 중인 Kernel을 다시 부팅하지 않고 Userspace만 새로 시작하는 방식입니다. 따라서 두 이미지의 Kernel 버전이 같아야 다음 단계의 soft reboot를 진행할 수 있습니다. 이번 실습에서는 두 이미지 모두 6.12.0-211.16.1.el10_2 Kernel을 유지해야 합니다.

yggdrasil이란?

yggdrasil은 RHEL 10에서 Hybrid Cloud Console의 메시지를 받아 호스트에서 원격 작업을 수행하는 daemon입니다. 올바르게 구성된 경우 Red Hat Lightspeed remediation plan에서 생성된 Ansible Playbook을 받아 실행할 수 있습니다. RHEL 9 이하에서는 이 역할의 daemon 이름이 rhcd입니다.

7-3. Console — 등록된 현재 시스템과 CVE 확인

7-4. 발견된 CVE에 대해 Remediation Plan 생성

Remediation Plan 생성과 원격 실행은 다릅니다.

현재 시스템이 Red Hat Lightspeed에 등록되어 Inventory/Vulnerability에서 CVE가 확인되면, 해당 CVE를 선택해 Remediation Plan을 생성하고 Ansible Playbook Preview를 확인하거나 다운로드할 수 있습니다. 반면 Lightspeed 콘솔에서 그 Playbook을 해당 RHEL 시스템에 직접 원격 실행하려는 경우에는 yggdrasil 기반 Remote Management가 활성화되어 있어야 합니다.

CVE 확인에서 끝나지 않고 remediation까지 연결할 수 있습니다.

Vulnerability 화면에서 대응할 CVE를 선택한 뒤 Plan remediation을 누르면 Red Hat Lightspeed가 해당 CVE의 수정 또는 완화 작업을 포함하는 Ansible Playbook 기반 remediation plan을 생성합니다. Plan을 만들기 전에 Preview를 다운로드해 실제 적용될 Playbook 내용을 검토할 수도 있습니다.
